**APL** (Abada Process Language) is the canonical, human-readable way to
define a workflow in Abada. A process is a YAML document (`abada.io/v1`) that
Studio serializes from its canvas and that the engine compiles *directly* into
the executable graph — no XML intermediate. BPMN remains supported as an
import and backward-compatibility format that Studio transpiles at the
boundary.

```mermaid
flowchart LR
    Canvas[Studio canvas] <--> YAML[APL YAML abada.io/v1]
    YAML --> Import[BPMN XML - transpiled on import]
    YAML --> Engine[Engine - AplParser, direct compile]
```

## Why YAML

- **Configuration as code.** A workflow is plain text a reviewer can diff and
  version-control, without a vendor XML vocabulary.
- **Comments are first-class.** Studio and AI-assisted tooling annotate
  workflows with rationale and policy references that never leak into
  execution.
- **AI-friendly.** Indentation-based structure and comments make APL a stable
  target for small, reviewable machine-generated diffs.

## Document structure

A document has exactly three top-level keys:

```yaml
version: abada.io/v1
metadata:
  key: lead_triage           # optional — derived from name when omitted
  name: Lead Triage
  owner: alice               # optional
  variables:                 # optional — what expressions may read
    - name: lead
      type: object
      required: true
flow:
  entry: onStart             # id of the single webhook start node
  nodes: [ ... ]
```

`metadata.key` is the immutable process key; without it, `metadata.name` is
sanitized into one (non-alphanumeric characters become `_`, lowercased). A
project can hold multiple process keys; each key versions immutably on every
deploy.

`metadata.variables` declares the start payload and any variable written by an
`engine-task`, `script` or `human-input` node. Once declared, the engine warns
about an expression that reads a name nobody declares or writes upstream — a
typo that would otherwise fail only when an instance reaches that node.

## Node vocabulary

| Node | What it does | Runtime element |
| --- | --- | --- |
| `webhook` | Single start node | Start event |
| `agent` | LLM call as durable external work (`abada:agent`) | External service task |
| `engine-task` | Any durable worker topic (system service, integration) | External service task |
| `script` | In-transaction server-side script | Script task |
| `decision-table` | Deterministic rules evaluated **in the workflow transaction** | Business rule task |
| `human-input` | Human task for the listed groups (optionally with a `formKey` form); `approval-gate` is a deprecated alias | User task |
| `condition` | Exclusive branch on `rules` | Exclusive gateway |
| `inclusive` | Fork/join on all matching `rules` | Inclusive gateway |
| `parallel` | Fork into ≥2 branches and join | Parallel gateway |
| `event-gateway` | ≥2 competing catch children; first to fire wins | Event-based gateway |
| `message-catch` | Durable subscription by message name + `correlationKey` | Message catch event |
| `timer` | Durable ISO-8601 duration wait | Timer catch event |
| `signal` | Durable broadcast subscription | Signal catch event |
| `end` | Terminal node | End event |

Every node shares `id`, optional `description` (the human-visible name — for
a `human-input` it is the task name), optional `next`, and an optional `ui`
layout hint. `condition` and `parallel` route through their branching keys
(`rules` / `branches`), never `next`; `event-gateway` routes exclusively
through its inline `events`. A `condition` branch matches with an
`if: "${...}"` expression and routes with `then: <nodeId>`; `else: <nodeId>`
marks the default flow.

## The doctrine: the table is the law, agents are the advice

- **`agent`** nodes are probabilistic advice: durable external tasks that a
  worker executes *outside* the workflow transaction.
- **`decision-table`** nodes are deterministic law: hit policies
  `FIRST | UNIQUE | COLLECT`, an explicit `otherwise` fallback, evaluation
  inside the transaction, and a `DECISION_TABLE_APPLIED` audit record. No
  match and no fallback fails loudly — never a guess.
- **`approval-gate`** puts a human between probabilistic and deterministic
  steps. Assignees are candidates; a `formKey` resolves to a project FORM
  resource whose fields bind by id to process variables.

## A compact example

```yaml
version: abada.io/v1
metadata:
  key: lead_triage
  name: Lead Triage
  owner: sales-team
flow:
  entry: onStart
  nodes:
    - id: onStart
      type: webhook
      description: Lead received
      next: classify
    - id: classify
      type: agent
      profile: abada.agent/v1
      model: gemini-3.6-flash
      prompt: |
        Classify the lead from ${lead.companySize}.
        Return exactly one value: HIGH, MEDIUM, or LOW.
      inputs:
        lead: ${lead}
      result_variable: lead_priority
      next: route
    - id: route
      type: condition
      description: Route by classified priority
      rules:
        - if: "${lead_priority == 'HIGH'}"
          then: review
        - else: done
          then: done
    - id: review
      type: approval-gate
      description: Senior sales review
      assignees: [lead-triage-human-reviewer]
      next: done
    - id: done
      type: end
```

Strict deployment validation rejects unbounded cycles, duplicate ids,
undeclared targets, a second `webhook`, invalid bounds and unrecognized node
types with index-friendly, stable error codes — atomically, persisting nothing.

## Loops: repeat a step, never forever

A process may go back to an earlier step — a reviewer rejects a draft and the
agent writes it again — as long as that step says how many times it may run:

```yaml
- id: draft
  type: agent
  loop: { max_iterations: 3, on_exhausted: escalate }
  next: review
```

The engine counts each pass in `draft_iteration` (handy in a prompt:
`this is attempt ${draft_iteration}`). After the third rejection the process continues
at `escalate`; without `on_exhausted` it stops at `draft` and opens an incident
that operators see. A cycle without a bound is rejected at deployment.

Each parallel branch counts its own passes, so two branches looping on the same
step are each limited separately. An operator resolves an incident by fixing
the cause and retrying it (the step starts a fresh pass) or by cancelling the
instance:

```bash
curl -X POST "$ABADA_URL/api/v1/process-instances/$ID/incidents/$INCIDENT_ID/retry" \
  -H "Authorization: Bearer $TOKEN"
```

A message wait opens an incident too when its `correlationKey` variable is
missing, instead of waiting for a message that can never match.

## Authoring surfaces in Studio

- **Canvas and YAML are one document.** The designer and the APL editor
  bidirectional-sync through a single document model.
- **Format badges.** Files show `[APL Native]` or `[BPMN Imported]`; the
  `abada.io/v1` language spec appears in Process Details.
- **Rule matrix inspector.** `decision-table` nodes edit in a matrix widget
  (inputs, ordered `when`/`then` rows, hit policy, `otherwise` toggle) that
  stays in sync with the canonical YAML.
- **Natural-language generation.** Describe the process; Studio scaffolds APL
  through the configured provider, with a deterministic local fallback.
- **Undo and redo.** Every edit of the open process — adding, deleting,
  connecting or moving nodes, node and process properties, auto-layout, an
  applied APL edit or an adopted AI proposal — can be undone with
  <kbd>⌘Z</kbd> / <kbd>Ctrl+Z</kbd> and redone with <kbd>⇧⌘Z</kbd> /
  <kbd>Ctrl+Y</kbd>, or with the arrows in the canvas toolbar. A drag or a
  burst of typing in one field is a single step. History is kept per process
  (100 steps) for the session; undone changes are autosaved like any edit.
  Text fields and the APL editor keep their own native undo.
- **Project file tree.** Projects are IDE-like workspaces seeded with
  `processes/`, `forms/` and `resources/` folders. Documents autosave with
  optimistic revisions; a stale save is rejected instead of overwriting
  another editor.

## Validating APL

The engine is the only APL validator, and Studio asks it directly:

- **While you type** in the APL editor, the draft is sent to
  `POST /api/v1/apl/validate` — the same checks a deployment runs, with
  nothing stored. Every problem is listed with its node; selecting one moves
  the cursor to the offending lines.
- **Errors** (`ABADA-APL-VALIDATION-001`) block **Apply to diagram** and
  **Deploy & Start**: a broken `next`, a model outside the engine's allow-list,
  an expression that is not valid CEL.
- **Warnings** never block. `ABADA-APL-SCHEMA-001` flags a field the engine
  does not know — usually a typo such as `confidence_treshold` — or a value of
  the wrong type. `ABADA-APL-VARIABLE-001` flags an expression that reads an
  undeclared variable.

<Aside type="caution" title="Warnings become errors at 1.1.0">
  In the 1.1.0 release candidates, schema violations are warnings so existing
  processes keep deploying. From 1.1.0 they reject the deployment; fix them
  now.
</Aside>

The model list and the field limits in the node settings come from the same
engine (`GET /api/v1/apl/schema`), so Studio never offers a model this
deployment would reject. Automation can call both endpoints too; see the
[API reference](https://github.com/bashizip/abada-platform/blob/dev/docs/reference/api-v1.md#apl-contract).

## Dry Run vs Deploy & Start

| | Dry Run | Deploy & Start |
| --- | --- | --- |
| Saves the document | No | Yes |
| Calls a model or tools | No — mock it | Yes, through a worker |
| Creates an instance | No | Yes, project-scoped |
| Error semantics | Local only | Durable, immutable version |
