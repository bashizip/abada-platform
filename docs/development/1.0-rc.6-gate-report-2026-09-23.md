# Abada 1.0.0-rc.6 publication gate report — 2026-09-23

## Decision

**GO — `1.0.0-rc.6` evaluation release candidate. Published 2026-09-23;
the tag workflow succeeded (see [Publication](#publication)).**

Local verification of the M1 "truth and safety" candidate is complete and
green, and the M1 exit demo passes after fixing the defect it found (see
[M1 exit demo](#m1-exit-demo)). The candidate is merged into `dev` and the
release owner signed off on 2026-09-23 (see [Sign-off](#sign-off)).

The tag workflow is part of the gate. A failure in image publication,
multi-platform manifests, archive publication, anonymous image access,
clean-runner installation or `/latest` promotion returns this decision to
**NO-GO**.

This candidate keeps the evaluation scope of the 1.0 RC line (see
`1.0-rc-publication-gates.md`, rc.1 and rc.5 scope sections): public-cloud
TLS/external-OIDC certification, multi-host failover, rolling upgrades,
production backup/restore, live telemetry certification, Windows quickstart
CI, image attestations and independent security review remain deferred and
are not claimed here.

## M1 exit demo

Reproduce with `./scripts/test/m1-exit-demo/run.sh`, which exits non-zero on
the first failing criterion (last passing run: `20260923183131`). Run on
2026-09-23 against the dev stack started with `scripts/dev/up.sh --no-build`
on the local rc.6 images, plus a demo overlay: a scripted
OpenAI-compatible model (counts every call; slow, invalid or low-confidence on
request), **two** agent-worker replicas, `ABADA_AGENT_LOCK_DURATION_MS=6000`
and a 30-second model latency, so every call outlives its lock five times and
any lock loss would let the other replica call the model again. Demo agents use
`gpt-5-mini` (allowed model, OpenAI-compatible route) with
`confidence_threshold: 85`, `max_attempts: 1`, `on_low_confidence` and
`on_invalid_output` routed to a human-input node.

| Criterion | Result | Evidence |
| --- | --- | --- |
| Malicious expression rejected at deploy | **PASS** | `Java.type('java.lang.Runtime').getRuntime().exec(...)` and a JavaScript constructor escape: HTTP 400 `BPMN_VALIDATION_FAILED`, node `route`, CEL suggestion; `/tmp/pwned` absent in the engine container. |
| Invalid or low-confidence output routes to a human | **PASS** | Schema-violating `URGENT` → outcome `INVALID_OUTPUT`, `lead_priority` not written, instance at `review`. Confidence 40 → `LOW_CONFIDENCE`, at `review`. Valid output → completed. One model call per case. A reviewer in `abada-task-user` claimed and completed a review; the instance completed with the reviewer's value. |
| 4 slow agent tasks, no duplicate model call | **PASS (after fix)** | Two rounds of four: 8/8 completed with outcome `OK`, exactly one model call per task, work split across both replicas (distinct worker ids), 58 heartbeats per round, zero lost locks, failures, abandons or completion retries. |
| Site and brief claims match the code | **PASS** | Claims checker (23 retracted phrases) passes; outdated PDF brief removed. |

**Defect found and fixed.** The first run completed only 2 of 4 slow tasks:
a heartbeat committing while the same task's completion request was in flight
made the completion fail with `409 CONCURRENT_MODIFICATION` (open-in-view kept
a stale copy from the worker access check), and the worker recorded a failure.
With retries left, that retry would have repeated the model call. Fixed in
`1a4ccec` (engine reloads the task under its row lock; PostgreSQL regression
test) and `938783b` (worker stops the heartbeat before reporting, retries a 409
completion once, unique worker id per replica). Both tests fail against the
previous code.

The demo also surfaced documentation drift, fixed in `ff9722b` and `9b23000`:
APL `assignees` are candidate groups (not usernames), the engine validates
`output_schema`, script steps are an opt-in sandbox, and APL deployment
failures no longer say "BPMN validation failed".
