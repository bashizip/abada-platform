# Abada 1.0 RC Publication Gates

This is the release-blocking sign-off checklist for every Abada 1.0 release
candidate. The roadmap defines what must exist; this document defines the
evidence that must be collected for the exact commit, images and archive being
published.

An unchecked item means **NO-GO**. Marking an item not applicable requires a
written justification and approval from the release owner. Evidence from an
older commit or image tag does not satisfy a new candidate.

## Gate 1 — Scope and repository integrity

- [ ] The candidate commit is on `dev`, reviewed, and contains only intended
  1.0-RC changes.
- [ ] `dev` is synchronized with the intended `main` base without rewritten
  shared history.
- [ ] `git status --short` is empty at the candidate commit.
- [ ] Maven version, API/observability version, Compose image tags, README,
  release notes and roadmap identify the same candidate.
- [ ] No generated output, `.env` file, token, password, private key, local
  database, log or IDE metadata is tracked.
- [ ] REST API v1, worker protocol v1 and database behavior have no
  undocumented breaking change.
- [ ] The supported BPMN and deployment matrices match the implementation.

## Gate 5 — Clean development deployments

Each scenario starts after `docker compose down -v` and completes with all
required services healthy.

- [ ] Telemetry disabled: authenticate, deploy the sample BPMN, start it,
  claim and complete the task, and inspect the completed instance.
- [ ] Restart the engine with an active task and verify persisted progress.
- [ ] Confirm the disabled profile contains no Collector, Prometheus, Jaeger,
  Loki, Alloy, Grafana or telemetry-health container.
- [ ] Confirm disabled mode creates no exporter thread, telemetry connection
  attempt or telemetry-related readiness failure.
- [ ] Bundled telemetry passes the same workflow.
- [ ] External OTLP passes the same workflow without starting the bundled
  telemetry stack.
- [ ] Development quickstart succeeds from an empty directory without a

## Gate 7 — Telemetry correctness and failure isolation

- [ ] `grafana/alloy:v1.18.0` is pinned and
  `./scripts/test/validate-alloy-config.sh` passes.
- [ ] Alloy starts with `--disable-reporting` and makes no usage-reporting
  connection.
- [ ] Alloy reads only the named `engine_logs` volume and has no Docker socket.
- [ ] Alloy positions survive a container restart without silently losing or
  replaying the full log history.
- [ ] Metrics, traces and logs appear in Grafana within two minutes.
- [ ] A workflow trace correlates to its logs through `traceId` and `spanId`.
- [ ] Export queues, retry counts, backoff and request timeouts are bounded.
- [ ] Stopping the OpenTelemetry Collector does not fail engine readiness or
  roll back workflow commands.
- [ ] Stopping Alloy or Loki does not fail engine readiness or roll back
  workflow commands.
- [ ] Restarting failed telemetry services resumes best-effort export without

## Gate 8 — Security

- [ ] Dependency and container-image security scans have no unaccepted

- [ ] Every gate above is complete with evidence for the recorded commit and
  image digests.
- [ ] Required CI checks are green.
- [ ] No unresolved release-blocking issue or critical defect exists.
- [ ] The final candidate worktree is clean.
- [ ] Release owner approves publication.
- [ ] Engineering approver confirms runtime and persistence evidence.
- [ ] Security approver confirms security evidence.
- [ ] Operations approver confirms deployment, backup and recovery evidence.
