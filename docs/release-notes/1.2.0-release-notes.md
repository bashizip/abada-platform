# Abada 1.2.0 release notes

**Planned for 2026-12-04.** This document is ready before publication. The tag,
the publication date and the gate report link are added when the release
owner gives the GO. It follows [1.1.2](1.1.2-release-notes.md).

Milestone M5 *Studio experience* (roadmap
[`docs/development/roadmap.md`](../development/roadmap.md), task specifications
[`m5-task-specs.md`](../development/m5-task-specs.md)). 1.2 is about seeing
what a process does. You can open an instance and tell at a glance which path
it took and why, start one and watch it run step by step, and fix a failed
step where it failed. It also brings forms with files, agents that read
documents, and an audit trail of every administrative change. The user-facing
summary is
[What's new in 1.2](https://docs.abadaplatform.com/release-notes/1-2/).

REST API v1 and worker protocol v1 stay backward compatible: every change is an
additive field or endpoint, except the behaviour changes listed below. Flyway
applies `V40` to `V44`, all additive. **RustFS is now a required service** of
every self-hosted installation. Upgrade the engine, Studio and the agent worker
together.

## See what an instance did (S1–S6)

- **The path taken (S2).** The engine records the flow each token took in the
  history (no schema change). On the canvas the path is dense, numbered and
  drawn on top. Decisions show the branch that matched, and steps that never
  ran fade out (hover to explore, or toggle to show all).
- **Paced playback (S3).** A running instance and a Dry Run play back at a
  calm, brisk or instant pace. The engine still runs at full speed: Studio
  replays the event stream and shows how far behind it is, with *Jump to
  now*. Incidents and terminal states are never held back.
- **Incident on the node (S4).** The failing node is highlighted, and *Retry*
  or *Retry on another model* sits in a card anchored to it. The retry plays
  out step by step.
- **Live audit trail (S5).** It opens when the instance starts, and its
  entries appear in step with the canvas. *Deploy & Start* opens the instance.
- **Operations redesign (S6).** An overview with KPIs and attention cards, and
  an instance view centred on the canvas, with a sticky header and a details
  drawer.
- **Motion foundation (S1).** Shared durations and easings, reduced motion
  respected, and design tokens instead of repeated colours.

## Build processes (S7, S8, S11, S12)

- **Every node editable in the properties panel (S7).** Decision tables come
  first: rules, reordering, and the engine checks each rule. The palette draws
  each node as the canvas does, and Operations shows the matched rule. With
  nothing selected, the panel edits the process itself (name, description,
  category, owner, declared variables).
- **Decision inputs as evidence.** A decision table keeps the input values it
  matched on, under the project's evidence policy (`V40`). Operations shows
  them next to the matched rule.
- **Forms (S8).** A task form's schema is **pinned when the process is
  deployed** (`V41`, `process_definitions.form_snapshots`), and the engine
  checks every completion against it (`422 FORM_INVALID`). Forms get
  sections, rows, steps, nine new field types, `visible_when`, and a compact
  layout that adapts to their length. The form designer opens as a large
  panel with preview, undo and a guard against losing unsaved changes.
- **Variables and JSON (S11).** One JSON viewer for variables and every
  payload, with a collapsible tree, search, copy path, a JSON view and markers
  on changed values.
- **AI drafting workspace (S12).** The AI bar can be pinned, collapsed or
  hidden (Cmd/Ctrl+K). A prompt opens a workspace where you refine the draft
  with a live diagram, its APL and a diff, then apply it to the canvas as one
  undoable change. Nothing is deployed and the engine is unchanged.

## Files in human tasks (S9)

- A `file` form field uploads to RustFS (S3-compatible object storage on your
  own servers). PostgreSQL keeps the metadata and state (`V42`,
  `process_files`), and the variable holds a reference, never the bytes.
- A file is attached in the task's completion transaction, without any call to
  the object store. It is read through the engine, with permissions, an audit
  entry and safe download headers. Deletion is a durable, idempotent sweep.
  Projects choose how long finished instances keep their files.
- Contract: [process files](../reference/process-files.md).

## Agents that read documents (S15)

- An agent node declares `files` (a name mapped to an expression that gives a
  file reference or a list of them) and `max_files` (1–20, default 5).
  Deployment compiles the expressions and refuses bad names, a name that is
  also an input, and `max_files` without `files`.
- When the work is locked, the engine checks each file against
  `process_files`, in the lock transaction: it must be `ATTACHED` to this
  instance, within `max_files` and within `abada.agent.files.max-bytes`
  (default 20 MB). The descriptor carries references (`resolvedFiles`), never
  bytes. A breach fails the work for good with `AGENT_FILE_INVALID` or
  `AGENT_FILE_LIMIT`.
- The agent worker downloads the declared files while it holds the lease and
  checks size and sha256 (`AGENT_FILE_INTEGRITY` on a mismatch). It sends them
  in each provider's format: images and PDF for Gemini, OpenAI and OpenRouter;
  images for Anthropic and other OpenAI-compatible endpoints. A model that
  cannot read a declared type is skipped; with none left the work fails with
  `AGENT_FILE_UNSUPPORTED`. A call is never made without its files.
- Each model call records the files the engine verified (`V44`,
  `agent_steps.files_json`): name, id, type, size and sha256. This is kept
  whatever the evidence payload policy, and after payloads are purged. Bytes
  are never journaled, logged or written to the worker's disk.
- Studio has a *Files* section in the agent properties and shows file chips
  (download plus sha256) on model-call steps. Example:
  `examples/apl/scanned-invoice.apl.yaml`.

## Administration audit trail (S10)

- `admin_audit_events` (`V43`): one row per administrative change. A change
  the database holds is written in its own transaction: projects and members,
  worker bindings, AI providers (never the key), tool credentials, evidence,
  file and Insight policies, deployments, rollbacks, proposal reviews and
  adoptions. Users and groups are changed in Keycloak, so their row is written
  once Keycloak has accepted the change.
- Refused calls are recorded as `DENIED`: 403s, and project role checks that
  answer 404 to outsiders.
- On PostgreSQL a trigger refuses UPDATE, DELETE and TRUNCATE for every role.
- `GET /api/v1/admin/audit` (filters, keyset cursor, `after=` for live
  updates), `/export` (CSV) and `/catalog`, for administrators only. Studio
  *Administration → Audit* has filters, live updates, a details drawer and
  CSV export.

## Documentation (S13, S14)

- Every page of the documentation names the release it describes. *New* and
  *Updated* badges come from page frontmatter. There are release notes pages
  per minor release, and Studio has *Documentation* and *What's new* links
  plus a *What's new* card after an upgrade.
- The build fails when the engine, Studio and documentation versions disagree
  with `documentation/release.json`.

## Also in this release

- Open event streams no longer hold a database connection (`open-in-view` off
  for every profile), so watching clients can no longer exhaust the engine's
  connection pool.
- The header tab follows the view's context, views switch with a short fade,
  *Back* returns to where an instance was opened from, and the canvas links to
  Operations.
- A welcome screen with an example run, and a sign-in page listing the four
  demonstration roles.
- Dependency updates for published advisories: DOMPurify, fast-uri, undici,
  Vite and zod (documentation); vitest, Vite and fast-xml-parser (Studio).

## Behavior changes

- **Task completions are checked against the pinned form** for processes
  deployed with 1.2. A value that breaks the form (a missing required field, a
  wrong type, a value outside its options or bounds, a file that is not
  attached or not allowed) returns `422 FORM_INVALID` with the violations.
  Processes deployed before 1.2 keep the unchecked live form until they are
  redeployed.
- **A malformed variable patch returns `400`** instead of being applied
  partially, and a job *Retry* is reserved for operators.
- **A worker's download of a process file** now checks the worker principal
  like the other worker endpoints. For an agent task, the worker gets only the
  files its node declares.
- **Insight replays stop at an agent that reads files** (`NEEDS_EXTERNAL`)
  instead of calling the model without the case's documents.
- **The deployment claims change from "PostgreSQL only" to "PostgreSQL and
  RustFS"** for self-hosted installations.

## Upgrade

See [Upgrading to 1.2](../operations/upgrading.md#upgrading-to-12-v40v44-rustfs-for-process-files).
In short:

1. Back up PostgreSQL, and keep `ABADA_ENCRYPTION_KEY` with the backup.
2. Add RustFS:
   - the one-line installer adds it on update;
   - production Compose needs `ABADA_RUSTFS_IMAGE`, `ABADA_FILES_ACCESS_KEY`,
     `ABADA_FILES_SECRET_KEY` and `ABADA_FILES_SSE_MASTER_KEY` in `.env.prod`
     (`doctor prod` checks them);
   - the server profile generates them on first start.
3. Start 1.2.0. Flyway applies `V40`–`V44`, all additive.
4. Wait for `/api/actuator/health/readiness` to report `objectStore` `UP`
   before sending traffic.
5. From now on, back up the RustFS volume and `ABADA_FILES_SSE_MASTER_KEY`
   together with the database.

## Rollback

Image rollback does not reverse a Flyway migration. 1.1.2 ignores the
`V40`–`V44` objects, so the engine can be rolled back without a restore, with
these consequences:

- forms are no longer checked;
- uploaded files stay in RustFS but cannot be read through 1.1.2;
- agents that declare `files` will not deploy;
- the audit trail is no longer written.

The `admin_audit_events` trigger stays, so the table cannot be emptied by
hand. Restore from a tested backup when in doubt.

## Known limitations

- **Files as agent input:** images and PDF only. Office and text files are
  planned for 1.2.x (N1).
- **Files sent to a provider:** a file sent to a model goes to that model's
  provider. Use a self-hosted vision model, or an OCR step on your own
  servers, if documents may not leave your infrastructure.
- **Provider wire formats** for files are tested against stub providers. Check
  one real document with the provider you use before relying on it.
- **Audit retention and SIEM:** the audit trail has no retention policy and no
  SIEM export yet; it can be queried and exported as CSV (both are 1.3
  candidates).
- **Replays** do not run tools, called processes, timers, messages or file
  reading.
- **Side effects outside the engine** remain at-least-once unless a tool
  proves an idempotency key. Multi-replica claims apply only to the PostgreSQL
  topology covered by the existing concurrency tests.
- **Certification:** public-cloud certification and an independent security
  review have not been done.
