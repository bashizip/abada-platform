# Abada 1.1.0-rc.2 release notes

Released 2026-10-10 — evaluation release candidate for milestone M3 *Agents
that act* (roadmap [`docs/development/roadmap.md`](../development/roadmap.md);
gate report [`1.1-rc.2-gate-report-2026-10-10.md`](../development/1.1-rc.2-gate-report-2026-10-10.md)).
Upgrade the engine, Studio and the Agent Worker together; see *Upgrade* and
*Rollback* below and [`docs/operations/upgrading.md`](../operations/upgrading.md).

Agents can now act: they call the tools of a project's MCP tool servers under
read, write and approval-required policies, a person approves each risky call
with its exact arguments, every model and tool call is journaled so a crash
never repeats a write blindly, turns, tokens and spend are bounded and priced
by the engine, an agent can choose the next step among declared routes, and
processes compose through call-process steps and agent delegation. Studio
follows instances live and shows every step an agent took.

REST API v1 and worker protocol v1 stay backward compatible: every change is
an additive field or endpoint. Flyway applies `V27` to `V33`, all additive.

## Tool servers and tool references (E7)

- A project **tool server** is a `TOOL_SERVER` resource (YAML, validated on
  every save): an MCP server reached over streamable HTTP, its tools and each
  tool's policy — `read`, `write` (with `idempotency: key | none`) or
  `approval_required` (with approvers).
- Agent nodes bind tools as `<server>/<tool>` or `{ ref, policy, approvers }`.
  Deployment resolves every reference against the project's tool servers and
  freezes the bindings with the definition version; a node may tighten a
  policy, never loosen it (`ABADA-APL-TOOL-002`).
- Tool credentials are managed per project
  (`PUT/GET/DELETE /v1/projects/{projectId}/tool-credentials/{name}`, values
  never returned) and issued only to the worker holding the lease of a task
  bound to that server. The engine never connects to a tool server.
- `ABADA_AGENT_ALLOWED_TOOLS` on the worker lists the tool servers it may
  reach; a deployment cannot widen it.

### Behavior changes

- A tool name without a server (`web_search`, the rc.x form) deploys with an
  `ABADA-APL-TOOL-001` warning and is passed to the worker as an advisory name;
  it is never executed and becomes an error at 1.1.0.

## The tool loop (E8)

- An agent that binds tools talks to the model over several turns and calls
  the tools it asks for, through the official MCP Java SDK.
- `max_turns` (per attempt, default 8), `max_tokens_total` and `budget_usd`
  bound the loop; reaching one ends the step with `AGENT_BUDGET_EXHAUSTED`,
  routable through `on_error` by code. A missing tool or a changed pinned input
  schema (`input_schema_sha256`) ends it with `TOOL_CONTRACT_MISMATCH`.

## The step journal and crash-safe writes (E9)

- Every model and tool call is journaled with the engine
  (`POST /v1/external-tasks/{id}/steps`) before it runs; fetch-and-lock returns
  the attempt's steps so a resumed lease continues without paying for a model
  turn twice.
- A write is journaled `STARTED` first. When its server takes a key, the
  engine gives it one that stays the same across leases and restarts. A write
  without a key interrupted by a crash is never re-sent: the step becomes
  `OUTCOME_UNKNOWN` and a `TOOL_OUTCOME_UNKNOWN` incident asks a person
  whether it happened (**It happened** / **It did not happen** in Studio).
- A write with the same tool and arguments that an earlier attempt completed
  is answered from the journal instead of being sent again.

## Approval-required tools (E10)

- An `approval_required` call is journaled as proposed: the agent's work parks
  (`AWAITING_APPROVAL`, no lease) and a `TOOL_APPROVAL` task opens for the
  approver groups, showing the tool, the arguments the evidence policy keeps
  and their digest.
- Approve or reject with `POST /v1/tasks/{id}/decision` (a rejection needs a
  comment, which the agent reads). An approved call runs once, with the
  approved arguments only. Only candidates decide; a worker credential never
  does. `approval_sla_hours` marks a late approval escalated.

## Evidence and cost (E11)

- Each journaled step keeps digests, tokens, timings and an engine-computed
  cost. Payloads are kept as the project's **evidence policy** allows
  (`PUT /v1/projects/{id}/evidence-policy`: `none`, `redacted` by default or
  `full`, with a retention period; a node may only be stricter), encrypted at
  rest and purged after retention.
- Payloads are read with
  `GET .../instances/{id}/agent-steps/{stepId}/payloads`, only by project
  members with the `abada-evidence-reader` role (not implied by
  administration); every read is recorded as `EVIDENCE_READ`.
- Model prices are effective-dated (`/v1/model-prices`, **Settings → Model
  Prices**). A call with tokens but no price is *unpriced*, never free, and a
  `budget_usd` fails closed for it. Instances carry `agentCost`.

## Live instances and the agent-step inspector (E12)

- `GET /v1/projects/{projectId}/events/stream` is a Server-Sent Events stream
  of the project's lifecycle events, identifiers only, served by any replica,
  resumable with `Last-Event-ID`, open to project members only.
- Studio's instance page and live canvas follow it and show **Live**, falling
  back to polling.
- The step inspector lists every model call, tool call and delegation per
  attempt: policy, state, approver and time, delegated child, tokens and cost;
  payloads on demand for evidence readers.
- The designer edits tools (from the project's tool servers, tighten only,
  approvers), loop limits, delegates and call-process inputs and outputs.

## Routing agents (E13)

- An agent node may declare `routes` (2–8, each with a description and an
  optional CEL `when`). The engine adds a required `route` to the output
  contract, accepts only a declared route, and treats a route whose `when` is
  false as an invalid answer. The route taken is stored in `<id>_route` and
  recorded as `ROUTE_TAKEN`.

## Call-process and agent delegation (E20)

- A `call-process` step starts a governed child process of the same project,
  pinned at deployment, with only the mapped inputs and outputs; the parent
  waits, a child failure takes `on_error` or opens a `CHILD_FAILED` incident,
  and cancelling the parent cancels its children. Depth is limited
  (`abada.call-process.max-depth`, default 4).
- An agent node may declare `delegates`: each becomes a
  `delegate:<process>` tool the agent may call; the engine checks the inputs
  against the child's declared variables, optionally asks a person to approve,
  starts the child and returns only its declared outputs to the agent.
- Lineage (`parentInstanceId`, `rootInstanceId`, depth, `startedByAgent`) is
  shown under **Called processes** on the instance page.

## Fixes found while writing the agent tutorial

Running the new tutorial end to end on an isolated stack found these defects,
fixed with regression tests:

- An agent could not finish after an operator confirmed an interrupted write:
  the confirmation stored no result, the resumed worker re-ran the call and
  failed, and each new attempt failed the same way (the write itself was not
  repeated). The confirmed fate is now stored as the call's result.
- The confirmation overwrote an approved call's approver with the operator.
  The approver is kept; the confirming actor is in the incident's history.
- A write repeated in a later attempt was matched on the model's call id as
  well as its arguments; models that change call ids between attempts would
  not have been matched. It is matched on the tool and arguments now.
- The event stream sent nothing until the first event or heartbeat, so a quiet
  project showed **Polling** for up to 15 seconds.
- Studio's project explorer dialogs rendered under the canvas.

## Documentation and examples

- New pages: **Concepts** (every capability, its guarantee and its limit),
  **Use cases** (five runnable processes) and **Tutorial: an agent that acts**
  (13 steps with screenshots). The architecture pages describe the tool loop,
  the step journal, approvals, delegation and the agent security boundaries.
- New examples: `refund-agent.apl.yaml` with the `payments` tool server, and
  `support-triage.apl.yaml` with `fraud-check` and `refund-payout`.
  `ExampleGalleryTest` deploys and starts every example on PostgreSQL.
- `scripts/dev/m3-demo/` holds a stub payments MCP server, a scripted model and
  Compose overlays for local runs.

## Upgrade

1. Back up PostgreSQL and keep `ABADA_ENCRYPTION_KEY` with the backup: tool
   credentials and journaled payloads are encrypted with it.
2. Upgrade the engine, Studio and the Agent Worker together. Flyway applies
   `V27`–`V33` (tool servers and credentials, the step journal, call-process
   lineage, prices and evidence, approvals, delegation, the event stream); no
   existing row is rewritten.
3. For agents that bind tools: set `ABADA_AGENT_ALLOWED_TOOLS` on the worker,
   add the project's tool servers and, for `budget_usd`, model prices.

Events written before `V33` are not replayed by the event stream; webhook
delivery is unchanged.

## Rollback

Rolling back to `1.1.0-rc.1` requires the pre-upgrade backup. The migrations
are additive, but rc.1 does not know tool server resources, approval tasks,
call-process steps or delegated children, and an in-place rollback with those
in use is not tested.

## Known limitations

- External effects remain at-least-once: a tool server must deduplicate with
  the idempotency key it receives; a write without a key that was interrupted
  needs a person to check the target system.
- Only MCP over streamable HTTP is supported (no stdio servers).
- The step inspector is on the Operations instance page; the live-canvas
  inspector shows the agent configuration and telemetry only.
- The combined M3 exit demo on two replicas was not run as one scripted demo;
  the gate report lists the evidence for each of its steps.
- The evaluation scope of the RC line is unchanged: public-cloud certification,
  multi-host failover, rolling upgrades, production backup/restore drills and
  an independent security review are not claimed.
